The largest recurring cost is GPT-5.4 mini query understanding because the current application calls it once per search. Azure AI Search is the second-largest fixed cost. Query routing and caching should be validated before production because bypassing GPT for deterministic requests can materially reduce the run rate.

Production Assumptions

  • 15 million active products; 80%, or 12 million, have an image.
  • 10 million searches/month; one GPT call per search at a blended 1,200 input and 150 output tokens across text and multimodal requests.
  • 80% text-vector searches, 10% image/combined searches, and 30% semantic reranking.
  • 5% monthly catalog churn, or 750,000 products requiring enrichment and reindexing.
  • Search Standard S2 with 3 partitions and 3 replicas for 1.5 TB storage, 450 GB vector quota, and query-plus-indexing SLA coverage.
  • Raw vectors are about 141 GB for one index and about 283 GB for active/candidate blue-green indexes before HNSW overhead; obsolete V1-V3 indexes are deleted.
  • Cosmos DB autoscale in two regions with 50,000 maximum RU/s and a 15,000 average hourly peak billing level per region.
  • Zone-redundant Container Apps autoscale from 3 to 30 replicas; 20 million active replica-seconds equals 7.6 continuously active replicas on average.
  • Approximately 3 TB Hot Blob storage and a $1,000 Front Door Premium/WAF, generated-thumbnail, transaction, origin-transfer, and egress allowance.
  • One full catalog rebuild per year is amortized into recurring cost.
  • 200 GB/month of telemetry with 30-day retention and 730 hours/month for provisioned resources.

Capacity Checks

  • Search storage: three new S2 partitions in Central US provide 1.5 TB.
  • Vector quota: three S2 partitions provide 450 GB; estimated raw vectors are 141 GB per index before HNSW overhead.
  • Index lifecycle: production keeps only active and candidate indexes; retaining POC V1-V3 is outside this sizing assumption.
  • Availability: three replicas provide Azure AI Search query-and-indexing SLA coverage.
  • Document count: 15 million is well below the 24-billion-document S2 limit.
  • Initial indexing: use checkpointed parallel batches; the current single-worker POC job is not a production loader.

Required Validation Before Commitment

  1. Load at least 1 million representative products into S2 and project full plus blue/green storage from Search statistics.
  2. Load-test all six search modes at retail-event peaks and adjust replicas from p95 latency and throttling.
  3. Measure GPT tokens and the percentage of requests that deterministic routing or caching can bypass.
  4. Measure Cosmos hourly peak RU, define edge authentication and thumbnail generation, and measure CDN/WAF traffic, cache-hit ratio, and telemetry ingestion.
  5. Confirm model quota and obtain negotiated enterprise prices before budget approval.

Important Notes

This is a single-primary-region Search/application planning estimate with two-region Cosmos DB, not full regional active/active disaster recovery. Representative testing is required before funding approval.
  • The 3-partition S2 design is a starting hypothesis. Search index size depends on tokenization, HNSW, vectors, and field attributes.
  • If blue/green vector usage exceeds quota, use vector compression, reduce dimensions, remove unnecessary stored vectors, add a partition, or move to S3.
  • Multi-region active/active hosting, a secondary Search service for disaster recovery, DDoS Network Protection, Defender plans, Azure support, taxes, and staff labor are excluded.
  • A secondary regional Search service would approximately double the Search line and add replication, hosting, and network costs.
  • Production image delivery should use thumbnails and CDN caching, not proxy every original image through FastAPI.
